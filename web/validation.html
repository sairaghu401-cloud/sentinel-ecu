What the suite checks

The built-in acceptance suite contains twelve synthetic cases. It includes clean traffic, all six attack families, analyst loss, safety recovery and checks that preserve fair evaluation.

CaseQuestion
Clean urban trafficDoes normal urban traffic avoid unexplained loss and false alarms?
Clean highway trafficDoes the gateway tolerate the second clean profile?
Spoofing, replay, flooding, fuzzing, payload and stealthDoes each seeded attack meet its defined behavioral checks?
Analyst disconnectedDo local gateway rules keep operating without the advisory path?
Safety latch and explicit recoveryAre request, acknowledgment, latching and recovery distinct?
Deterministic seeded replayDo the same inputs reproduce the modeled result?
Evaluator label isolationCan labels change scoring without changing detector decisions?

Results on this page describe the methodology. The laboratory produces the actual pass/fail report when you run validation; no run is started by reading this page.

Read the metric population

Precision, recall, false-positive rates and the confusion matrix are computed from labelled frames. Unknown ground truth is excluded from that scoring population. Empty denominators remain unavailable, rather than becoming a fabricated perfect score.

The ID-allowlist baseline and the gateway receive the same labelled population for comparison. Queue drops remain availability loss. They are not promoted to detection success.

Modeled end-to-end latency includes the CAN/gateway model. Host processing time measures work on the current machine. Neither is a measurement from a physical STM32 or Raspberry Pi.

Reproduce an experiment

01

Set a baseline

Choose a profile and seed. Reset, then run clean traffic before adding an attack.

02

Change one condition

Keep target, duration and seed fixed when comparing intensity. Record whether the analyst is connected.

03

Inspect and export

Use the traffic inspector to read frame decisions. Export CSV or JSON before resetting or closing a browser session.

04

Run the acceptance suite

Open Validation in the laboratory. Wait for all cases to complete and download the experiment report.

What the results establish

These experiments validate specified behavior of a deterministic software model. They do not establish real-vehicle safety, hardware timing, regulatory certification or generalization to all CAN datasets.

  • Two modeled 500 kbit/s classical CAN segments, six configured standard identifiers and a defined payload schema.
  • A statistical analyst trained on separate synthetic data, with modeled delay and bounded processing queues.
  • Trace replay constrained by the laboratory schema. Arbitrary IDs may correctly be rejected as unknown.
  • Finite evidence retention. Exported evidence describes the retained population and its provenance.
  • No physical vehicle, controller or actuator is connected.

Source, tests and design documentation are available in the project repository.
